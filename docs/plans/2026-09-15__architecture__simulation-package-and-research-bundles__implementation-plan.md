# MateriaSim：基础组件、场景流程与研究包实施方案

## 1. 决策与范围

把 MateriaSim 建设成“一套模拟核心，组合出多种场景，再由统一研究包组织不同研究任务”的项目。

这里的研究包是有统一约定的研究源码目录，不是每个课题单独安装的 Python 包。研究包引用平台能力，不复制 runner、检查点逻辑、参数解析或通用分析算法。

本轮优先交付三个实际结果：

1. 能在任意工作目录使用的 `materiasim` Python 包，源码不再和课题、模型模板、计算结果混放。
2. 现有 ZIL/CAT/ANI 场景继续使用同一条构建、运行、续跑和分析链路，整理前后有可核查的回归证据。
3. 一个能够声明多个实验条件与重复、生成有界任务清单、逐项调用现有核心并汇总全部结果的研究包闭环。

不把“先搭框架”解释为创建大量空目录、空后端或占位接口。先用已有材料把结构和研究工作流验收，再按真实需求增加混合溶剂、聚合物、固相和纳米界面。

## 2. 当前基线与真正需要整理的地方

下表保留实施前的定位基线；拆分后的实际责任以当前[模块 README](../../docs/guides/simulation.md)和源码为准。现有工程核心已经可复用，不需要推倒重写；问题主要是代码责任、可复用资产、示例与课题边界仍混合。

| 当前情况 | 具体问题 | 本方案处理 |
|---|---|---|
| 核心在 `materials_simulation/materials_sim/` | 从模块目录启动或设置 `PYTHONPATH`，项目名与导入名不同 | 建立可安装的 `src/materiasim/` 包与统一入口 |
| `examples/` 同时包含实验、模型卡、相互作用包和协议 | 很难判断哪个是示例、哪个是共享依赖 | 拆为示例配置与 `catalog/` 共享资产 |
| 示例引用两个旧案例目录中的坐标、ITP、MDP | 不能把旧案例目录当废弃副本直接删除 | 先清点引用闭包，再逐项迁移共享资产 |
| `assembly.py` 同时管数量/区域与 GAFF 参数合并 | 引擎无关装配与 GROMACS 表达混在一起 | 按职责拆分，不整体改名搬进通用构建器 |
| `packmol.py` 从 `gromacs.py` 导入进程调用 | Packmol 不应依赖 GROMACS 才能调用外部工具 | 提取通用进程管理，保留各工具专属逻辑 |
| `protocol.py` 同时校验阶段并派生 MDP | 后续其他引擎不能共用 MDP 假设 | 阶段语义与 GROMACS 参数编译分开 |
| 已有 Experiment、Run、attempt 与独立分析 | 没有完整的多实验/重复研究编排 | 增加轻量研究层，不创建另一套运行状态机 |
| 有内容哈希、冻结输入和严格恢复身份检查 | 搬包会改变源码身份；旧 Run 不能自动接着跑 | 历史读取保留，执行版本兼容明确拒绝或显式迁移 |

当前已验证范围仍是 macOS CPU 下的已有模型短程子集。已有自动装配支持整数数量、TIP3P 填水或无水周期盒；后者不是固相、熔体或非周期真空支持。混合溶剂、聚合物、生物大分子、真实固相、界面、Linux/GPU 仍不能算本轮框架整理的既成能力。

## 3. 三层结构与依赖方向

### 3.1 基础组件：完成单一、可验证的工作

包括模型与参数引用、几何装配、引擎格式编译、进程执行、阶段交接、状态/证据保存、观察量计算。组件通过明确输入/输出协作，不通过课题目录名判断行为。

组件不是“为每种材料写一套计算系统”。同一装填器可以用于满足其约束的不同模板；同一引擎可以运行不同场景；同一接触分析可以服务多个课题。是否适用必须由参数、结构及观察量要求共同决定。

### 3.2 场景流程：组合组件并限定适用条件

场景回答“怎样构建这个体系”，例如导入既有溶质后加水、按数量装填分子后加水、构建链后装填或构建表面后放置液体。

场景不拥有独立 runner；只返回经过检查的构建步骤和构建产物。模拟协议、CPU/GPU 资源及分析任务分别指定，不写死在某种材料场景里。

### 3.3 研究包：组织研究问题与实验比较

研究包回答“为什么算、比较哪些条件、做几次、看什么、哪些结果会否定假设”。它生成普通实验配置，调用同一模拟核心，引用 Run 和分析证据。

逻辑关系：

```text
研究定义 + 显式实验条件 + 重复/种子 + 预算
                    ↓
           冻结的有限任务清单
                    ↓
         同一 Experiment / Run 工作流
                    ↓
   场景构建 → 引擎编译 → 执行/续跑 → 独立分析
                    ↓
         全部任务的比较与证据报告
```

代码依赖约束：入口/研究层调用工作流；工作流编排场景、构建器、引擎和分析；它们复用底层契约、进程及存储工具。底层模块不得反向导入 CLI、研究包或具体课题；通用进程模块不导入引擎；引擎间不互相调用。

## 4. 目标目录与命名

下列是拟议目标，不是当前目录实况。目录只在有实际内容、实现和测试时创建。

```text
MateriaSim/
├── README.md                     # 安装、最短使用、已验收能力与限制
├── pyproject.toml                # 包元数据、入口与明确的依赖边界
├── AGENTS.md                     # 公共授权与证据保护规则
├── src/materiasim/
│   ├── __init__.py
│   ├── __main__.py
│   ├── cli.py                    # 薄入口，不放科学算法
│   ├── specs/                    # 模型/实验/阶段/分析输入约定
│   ├── workflows/                # build/run/resume/analyze 的共用编排
│   ├── scenarios/                # 已实现的场景规则与步骤组合
│   ├── builders/                 # 引擎无关的计数、区域、装填工具
│   ├── engines/gromacs/          # GRO/ITP/MDP/TPR、预处理、执行与检查点解释
│   ├── runtime/                 # 通用进程、预算及运行状态支持
│   ├── analysis/                # 水化/组分接触等实际算法
│   ├── research/                # 研究定义校验、任务展开和比较
│   └── storage.py               # 内容哈希、原子写入、路径与证据存储
├── catalog/
│   ├── models/                  # 模型卡与小型冻结坐标/参数
│   ├── interaction_bundles/     # 被声明为可组合的精确模型集合及约束
│   └── protocols/               # 可复用的协议配置与引擎模板
├── examples/                    # 最小可执行实验，引用 catalog
├── profiles/                    # 执行资源配置；随 CPU/GPU 实现落地
├── studies/                     # 统一结构的研究源码包
├── tests/
│   ├── unit/
│   ├── integration/
│   ├── acceptance/              # 真实工具与小量计算验收入口
│   └── fixtures/                # 小型、固定、必要的测试输入
├── docs/
│   ├── architecture/           # 已落地的边界与设计决策
│   ├── guides/                 # 按真实接口编写的操作指南
│   ├── validation/             # 已有验收文档的规范归属
│   ├── plans/                  # 本文及其他未完成方案
│   └── ai/
└── skills/                     # Agent 操作指南，不承担程序校验
```

第一批不创建 `engines/lammps/`、聚合物插件树、数据库服务、工作流 DSL 或分布式调度器。没有真实实现的能力只列在计划与能力矩阵里，不用空函数伪装已接入。

命名约定：

- 产品/仓库名为 MateriaSim；拟议导入名和命令名统一为 `materiasim`，是否在 PyPI 可用不在本方案中作保证，也不包含发布。
- Python 文件、研究目录和配置文件使用表达用途的 `snake_case`；避免 `new`、`final2`、`common_utils` 等模糊命名。
- 新配置用 `schema_version` 表达数据格式；模型修订用显式版本与内容哈希，不依赖文件名中的“最新版”。旧文件名属于来源证据，迁移前不机械改写。
- 核心代码不得通过 `../../zwitterion_hydration_md/` 查找运行依赖，也不得假定当前工作目录是仓库根。
- `catalog/` 初期是本地文件目录，不实现在线市场或全局注册数据库。共享输入必须存在并可校验，名称不能替代内容身份。
- 可安装代码与科研资产分开：安装包不隐式获得仓库全部模型；实验必须显式提供资产路径。若核心确需内置小模板，必须明确纳入发行包并验证安装后可读。

采用 `src/` 的直接目的，是避免开发目录恰好可导入而安装包缺文件的问题；开发安装和构建后的发行包都要测试。[Python Packaging：src 与 flat 布局](https://packaging.python.org/en/latest/discussions/src-layout-vs-flat-layout/)。包元数据和命令入口集中于 `pyproject.toml`；依赖调整在实施时单独确认。[Python Packaging：pyproject.toml 指南](https://packaging.python.org/en/latest/guides/writing-pyproject-toml/)。

## 5. 基础契约：分别保存什么

以下名称描述目标责任，不要求全部做成类或继承体系。优先使用现有可序列化结构与边界校验，只有实际需要才拆出新对象。

| 契约 | 必需内容 | 不应承担 |
|---|---|---|
| 组分声明 | 身份、模型引用、明确数量；需要时含链长、端基、序列、质子化或表面修饰 | 自动猜测力场、电荷或化学连接 |
| 模型资产 | 分辨率、坐标/连接/参数、来源、文件哈希、适用引擎与已知限制 | 混入某课题的运行步数与 GPU 编号 |
| 相互作用包 | 精确模型集合、混合规则及显式交叉项、单位约定、适用范围与验证证据 | 因力场名称相同就默认可任意混用 |
| 场景输入/构建结果 | 边界、几何、装配规则；实际原子/组分数量、盒子、映射和构建来源 | 仅凭场景标签宣告相态或平衡 |
| 协议 | 有序阶段、积分/控温压、步长、目标步数、速度/检查点交接、输出要求 | 绑定某一 GPU 或机器路径 |
| 实验定义 | 组分、模型包、场景、协议、用途与分析请求 | 批量执行状态 |
| 执行配置 | 工具身份、CPU/GPU、墙钟/存储/尝试预算 | 自动改变科学协议使任务跑通 |
| 分析请求/产物 | 源 Run 与阶段、选择、单位、时间窗口、算法版本和结果身份 | 隐式修改源 Run 或把缺失量补出来 |

跨组件关键交接必须校验原子顺序、连接、组分/实例映射、总电荷、边界、单位、文件哈希。最终结构记录“请求数量”和“实际数量”，填水数不能偷偷转成用户指定浓度。

能力检查返回“支持/不支持及原因、适用条件、验证证据”；框架支持、实际工具可用、数值验收、科学验证分别记录。模型包含 `engineering_only` 限制时，研究包不能通过修改用途绕过。

## 6. 场景如何落地和扩展

首版保留现有场景标识及实际行为。拆分内部实现不要求用户重写所有实验配置。

| 场景族 | 首版落地 | 后续添加能力的前提 |
|---|---|---|
| 预建水盒 | 保留 `prebuilt_solute_water`、`prebuilt_mixture_water`，复用结构检查与加水链路 | 其他预建体系必须明确结构/模型与边界 |
| 按数量装配的周期盒 | 保留 `packed_liquid`，已有模型＋TIP3P 填水或不填水 | 混合溶剂需选定独立模板、完整参数与交叉作用证据 |
| 聚合物单链/溶液/熔体 | 本轮只确定交接字段，不创建假构建器 | 选定家族、链长/端基/立构、链内连接/参数及初态检查；共用 Packmol 不等于已实现链构建 |
| 生物大分子 | 与合成聚合物分开登记能力 | 序列/结构、缺失原子、质子化及专用模型预处理验收 |
| 晶体/非晶固相 | 本轮不把无水盒重命名成固体 | 晶胞/表面或制备协议、适用势函数与目标引擎验证 |
| 颗粒与固液界面 | 在真实固相和液体能力之上增加 | 表面化学、跨组分作用、周期/真空层及吸附等观察量定义 |

场景实现只选用已注册、可测试的步骤组合；首版用普通函数和显式分派即可，不开放任意 Python 表达式或配置脚本执行。

每增加一个场景，至少交付：适用约束、构建实现、完整参数来源、一个正例、关键拒绝负例、真实受限计算与观察量检查。科学可用性另按目标物性验收。

## 7. 统一研究包：源码结构与最小字段

拟议研究包示意：

```text
studies/<research_id>/
├── README.md                    # 问题、依据、对照、限制与使用方法
├── research.json                # 研究定义及显式任务设计
├── experiments/                 # 完整实验配置，引用共享 catalog
└── references/                  # 可选：来源清单/必要小型材料，不默认下载论文
```

首版不要固定创建空的 notebooks、scripts、reports、results。分析请求先沿用实验配置已有字段；只有确实多个实验复用同一分析定义时才提取独立文件。

研究专属方法可以保留为受测试的小型代码，但不能复制通用构建/执行/续跑逻辑；不从研究配置自动加载任意可执行代码。形成真实跨研究复用后，再将算法提升到核心。

`research.json` 的首版字段设计：

| 字段（拟议） | 规则 |
|---|---|
| `schema_version`、`id`、`revision` | 研究源码修订标识；不是新的模拟 Run 身份系统 |
| `question`、`hypothesis` | 明确问题与可否定预期；工程验收也须说明判定目标 |
| `purpose` | 与实验及模型允许用途一致；初版只承接现有工程短测 |
| `baseline_case`、`varied_factors`、`controlled_factors` | 指定基线、有意改变的条件及应保持一致的条件 |
| `observables`、`decision_rules` | 观察量定义/单位、比较范围、失败与采样不足的判定 |
| `cases` | 显式列出条件 ID、实验文件与重复记录；拒绝同名重复任务 |
| `limits` | 任务数、串行度、计算/构建/分析及存储上限和停止条件 |
| `sources` | 模型/协议/方法及研究设计来源，不用猜测的文献占位 |

第一版采用显式条件列表，不做任意字段覆盖或无界笛卡尔积扫描。条件对应完整实验文件；重复记录只允许白名单中的构建种子、首段速度生成种子及标签，展开后保存完整配置。模型、电荷、温压、步长不能通过“重复参数”改变。

同一重复的速度继承段不得重新生成速度。同一输入与种子不保证跨平台轨迹逐位相同；冻结实际构建结果与有效引擎输入才是运行证据。

研究问题、模型含义、观察量或比较设计改变时必须显式修订定义；已声明条件下的新种子/新运行记录为新 Run。沿用 Experiment/Run/attempt，不额外引入 Program/Study 执行状态机。

## 8. 研究包怎样调用核心

### 8.1 执行前展开并冻结任务

流程为：校验研究定义 → 校验全部引用与实验 → 展开有限任务 → 计算预算 → 明确输出根 → 保存冻结任务清单 → 逐项调用普通构建/运行入口。

冻结清单至少包含研究定义哈希、所有实验与传递依赖哈希、实际种子、协议/分析请求、工具要求、执行配置、任务总数和预算。路径用于定位，内容身份用于校验；拒绝引用逃逸到未获准输出位置。

仅校验或向标准输出预览计划不产生 Run；显式要求保存计划文件才写派生计划。构建可能调用 Packmol/GROMACS，不能把 build 宣称为纯查询。

### 8.2 第一版串行执行，不再造调度系统

- 一次只运行一个任务；不做并发抢 GPU、远程提交、无限重试或自适应搜索。
- 批次登记表只记录任务到已有 Run/AnalysisRun 的映射与调度事件；真正运行状态始终从 Run 读取，不能两边各维护一份 completed 状态。
- 启动前锁定登记表并原子保留任务与 Run 目标，防止两次启动同一任务。若崩溃发生在构建交接中，恢复时核查登记及 Run 实际证据；不确定时拒绝自动重建，不能凭缺少成功条目重复计算。
- 一个任务失败，保留全部证据；首版停止后续执行并报告未启动项。是否继续必须明确，不能自动换种子或减组分重试。
- 可恢复中断仍走原有 resume。完成/封存失败不原地重开；新尝试若需新 Run，登记父关系与原因，不能把失败覆盖为成功。
- 每次启动核对单任务剩余预算和整个批次累计预算；构建、编译、退出宽限和分析也计入，不能只累计 mdrun 参数。
- 重复提交相同冻结清单应返回已有登记或明确冲突；不自动生成一组“看起来相同”的新任务。

### 8.3 输出位置与证据关系

拟议外部输出布局（由用户选择实际路径，不是仓库内新增目录）：

```text
<external_run_root>/
├── batches/<batch_id>/          # 冻结任务清单、调度事件、Run 引用
├── runs/<run_id>/               # 沿用核心冻结输入、阶段、attempt 与状态
├── analyses/<analysis_id>/      # 原 Run 外部的独立分析
└── comparisons/<comparison_id>/ # 引用明确分析产物的派生比较
```

批次标识只是这次任务清单的审计身份，不替代实验/Run。普通运行不改 `studies/` 源码、文献笔记、目录索引、模型批准状态或旧报告。失败、未启动和分析失败均列入最终汇总，不只展示成功样本。

研究入口已实现为 `materiasim research validate/plan/run/status/compare`，其中 plan 默认预览，保存必须显式指定位置。已实现子集、真实参数和预算限制见[研究指南](../guides/research.md)；本文的其他长期设计仍不构成现成接口。

## 9. 第一份可交付的研究包

先做“已有 ZIL 水体系的数量变化与重复编排工程验收”，不等待用户选定新聚合物，也不把小量短测包装成科学研究完成。

设计从当前 [packed_zil_water.json](../../examples/packed_zil_water.json) 派生，原示例不覆盖：

| 项目 | 拟议固定设计 |
|---|---|
| 目的 | 验证研究包能正确表达两个条件、四个独立 Run、种子记录和完整汇总 |
| 条件 A | ZIL 总数 2；区域计数保持与该总数一致 |
| 条件 B | ZIL 总数 4；显式调整区域计数，其他声明条件一致 |
| 重复 | 每条件 2 次，合计最多 4 个 Run |
| 种子 | 展开前显式列出 4 对不同的装填/速度种子并冻结，不运行后挑选 |
| 模型与协议 | 沿用当前精确参数包、TIP3P、4.5 nm 周期盒与受限工程协议；原模板不改 |
| 观察量 | 实际组分数、映射、阶段完成及现有组分接触计数；接触阈值显式以 nm 记录 |
| 计算限额 | CPU 2 线程、串行；每 Run 最多 2 次执行尝试、每次 mdrun 墙钟参数 180 秒；同时受原每段步数上限约束 |
| 批次限额 | 总墙钟含构建/编译/分析与退出宽限最多 30 分钟，存储最多 1 GiB；预检不足即停止，不自动扩预算 |
| 停止 | 构建/参数/身份/数值错误立即停；时间或容量预算耗尽不继续启动后续任务 |

这些是后续实施验收的建议预算，不是本次启动计算的授权；若实测不能满足，报告未完成项并重新确认，不提高限制硬跑。

数量改变会影响填水后的实际水分子数，必须报告最终组成；不能声称这是严格固定浓度或固定水数对照。原始接触数量也会随分子对总数变化，不直接据其大小比较结合能力。

工程验收成立需四个任务按声明构建，结果均有身份与来源，成功/失败无遗漏，重复运行不会重复提交，批次报告可追到每个 Run。两次短重复不足以证明平衡或独立统计采样；不输出未经实现的置信区间或水化机制结论。

ZIL/CAT/ANI 三组分水盒及无水盒继续作为底层场景回归，不把物理条件不同的回归例混入上述研究的可比样本。

## 10. 比较、质量门与 Agent 操作

比较器先核对研究声明的变化，再检查未声明差异：模型/水模型、分辨率、协议、选择集合、截断、单位、阶段、时间窗口和归一化定义。不同条件可以按研究设计比较，但不能悄悄将不同统计定义合并。

第一版仅支持现有单阶段分析产物的工程汇总。跨阶段时间拼接、平衡段识别、自相关、有效样本量、误差传播等，未实现前明确标为不可用；不得以每帧数作为独立样本数。若需要科学推断，先扩展并验收对应方法。

质量门分四类：

1. 输入完整性：模型和交叉作用完整、坐标/拓扑相符、组成与边界有效。
2. 执行完整性：目标步数/时间、实际输出、检查点与日志一致。
3. 分析有效性：观察量所需数据存在、时间/选择/单位正确、全部结果可追溯。
4. 科学适用性：模型验证范围、平衡和采样证据满足具体问题；不能从前三项自动推出。

Agent harness 沿用根 AGENTS、项目 Skills 和程序入口。新增研究流程指导只能引用已实现命令；授权、预算、白名单与状态保护必须由程序落实，不能只写在提示词中。

Agent 可在授权范围内生成研究配置、预检、解释任务清单并执行限定短测；不得自动换模型、扩大预算、删失败证据、修改历史报告或将工程模型提升为生产批准。新增依赖、长计算、数据移动及服务器操作分别确认。

### 11.1 资产迁移不能只替换路径字符串

先生成“引用方 → 模型卡/协议 → 直接和间接文件”的清单，区分模板、有效参数、原始参数化资料和历史产物。只有当前依赖的资产进入 catalog，不批量搬入旧环境和全部结果。

若模型卡或协议引用位置改变，其 JSON 内容哈希可能改变，相互作用包的引用也需产生对应新版本；保留旧版及迁移记录，不能只修改旧 Run 的哈希使之通过。

记录原路径、新路径、原文件哈希、转换说明及验证结果。坐标/参数文件的纯移动保持字节；必须调整 include 时保存原件与派生件，校验有效拓扑、原子顺序及必要的固定帧能量/力对照。

安装态力场库与许可证单独核查。现有 bundle 对其内容身份的要求不能因移动而放松；不未经确认把整套外部力场或受限资料打包进公开仓库。

### 11.2 旧 Run、环境与保留文件

- 当前 [state.py](../../src/materiasim/runtime/state.py) 的读取完整性检查与执行源码身份检查已经分开。搬包后可读取旧 Run，不代表能用新源码恢复其执行。
- 保留只读历史读取/重分析测试；不编辑旧 manifest、哈希、检查点或封存状态。需要继续旧任务时使用对应代码/环境，或走另行设计、测试、批准的派生迁移，不加 force 绕过。
- 源码身份扫描必须覆盖拆分后的实际包与执行相关资源；不能因目录加深漏记实现。代码升级、参数变化和存储格式版本分开管理。
- CPU/GPU 方案提出的新执行格式只升级一次；单纯换目录不先创造另一套 v3。资源格式实施时统一明确旧格式只读和迁移策略。
- 不移动 `.venv-macos-analysis/` 后继续使用；在环境调整获准后按平台重建并验证，新环境通过前保留现有环境。
- 根目录旧计算输出和检查点继续原位保留；本文不授权清理。历史生成结果不因“研究包统一结构”而自动搬入 Git。
- 现有公共 Git 历史不重写、不 force push。后续源码迁移按普通可审查提交推进；本次不执行 Git 写操作。

## 12. 实施顺序与每批完成标准

| 批次 | 工作范围 | 完成标准 | 明确不包含 |
|---|---|---|---|
| A：基线与责任拆分 | 资产引用清单；提取通用进程；分开协议/装配中的 GROMACS 逻辑 | 原命令语义与现有测试保持；当前四个装配示例可校验；关键负例不放松 | 搬全部历史数据、增加材料 |
| B：包与共享资产迁移 | 安装包/新入口；迁移核心、测试、必要 catalog、示例和文档引用 | 仓库外可调用；开发安装与发行包均通过；不再依赖旧案例路径提供新任务输入 | 上传 PyPI、改力场、清旧环境 |
| C：研究定义与计划 | 研究 schema、显式条件/种子展开、冻结清单、预算预检 | 不调用引擎即可审查全部任务；篡改、无界任务、非法重复字段被拒绝 | 启动长任务、任意脚本执行 |
| D：研究执行与工程比较 | 串行任务登记、核心调用、恢复核查、全部结果汇总 | 第 9 节四任务闭环；中断/失败/重复提交测试通过；原 Run 不被分析改写 | 科学置信区间、自动寻优 |
| E：共用 CPU/GPU 执行层 | 按已有执行方案 E1—E4 增加资源配置与有界长任务基础 | CPU 真实回归、GPU 参数/拒绝逻辑测试；平台与设备证据明确分开 | 没有 GPU 时宣布 GPU 验收 |
| F：选定材料与服务器验收 | 按 M3—M6 逐项扩展；具备服务器后做执行方案 E5 | 每个材料场景有明确参数与真实验收，GPU 有实际卸载证据 | 宣称任意组合都能模拟 |

A、B 先完成职责和真实安装边界；C、D 紧接着交付研究使用能力，避免长期只有目录整理。C 可以先设计资源引用，D 首版用固定 CPU 短测预算；E 落地时替换为同一执行配置，不长期保留研究层独立的资源解释器。

研究包字段版本与 Run 存储版本独立，不因为新增研究描述就让所有已有 Run 失效。迁移过程中只维护一个新任务执行核心；必要的旧入口适配必须有真实调用方、测试和退出条件。

在没有选定新体系、没有 GPU 的情况下，A—D 可以构成一轮完整且有用的交付；E 可做本地实现与 CPU 验收。F 不能通过搭框架一并承诺完成。

## 13. 验证矩阵与验收门槛

| 层级 | 必须检查 |
|---|---|
| 文档/引用 | 所有当前路径可定位；目标路径明确标拟议；AGENTS/Skills/README 同步真实命令；历史事实不改写 |
| 安装 | 从仓库外执行查询/校验；构建后的发行包安装可用；不依赖当前工作目录、旧案例目录或隐式 PYTHONPATH |
| 单元 | 原解析/参数合并/几何/阶段/状态/分析测试；新依赖方向、研究字段/种子/预算及比较前置条件 |
| 集成 | 完整依赖冻结、源码身份覆盖、计划幂等、任务登记崩溃恢复、源文件变更拒绝、只读查询不调用构建 |
| 真实 CPU | 保留既有水/无水场景短测；关键构建/阶段改动做实际中断恢复与观察量独立对照；第 9 节研究包闭环 |
| 历史兼容 | v1/v2 证据可读、完成态缺文件/篡改仍拒绝；新源码不能绕过旧 Run 恢复身份；新分析不写原 Run |
