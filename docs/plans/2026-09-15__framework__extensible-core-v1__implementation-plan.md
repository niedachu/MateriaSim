# MateriaSim 可扩展框架第一版：具体改动方案

## 1. 决策、目标和完成边界

### 1.1 本轮要完成什么

先把框架做成能够承接多组分、多场景研究的工程基础，再通过具体模拟逐项扩展和验收材料能力。现在不要求用户确定最终研究体系；沿用已有 ZIL/CAT/ANI 和水/无水周期盒作为工程回归输入。

框架第一版的目标是：

> 在已定义的契约内，增加一种构建方法、场景或分析，只增加所属实现、能力登记和测试，不修改研究调度、Run 生命周期和证据管理的核心逻辑。

这不是“所有未来需求都不需要改核心”的承诺。反应性模型、可变拓扑、多尺度耦合等超出首版契约的能力，需要后续独立设计。

本轮不自研 MD 积分器、势函数计算内核、CUDA 算法或通用化学信息学库。GROMACS 继续承担数值计算；MateriaSim 负责体系与协议的组织、适用性检查、受控执行、结果契约和来源追溯。

### 1.2 必须分开的三个完成状态

| 完成状态 | 可以声明 | 不可以声明 |
|---|---|---|
| 框架本地完成 | 契约、CPU 实现、GPU 静态逻辑、迁移和工程回归通过 | GPU 已实测、任意体系已支持 |
| 指定环境工程验收 | 某平台、引擎构建、资源配置和体系短程贯通 | 已平衡、已收敛、物性可信 |
| 指定体系科学验收 | 明确模型、条件、性质和误差范围内的验证结论 | 推广到未验证材料、相态或组分组合 |

科学验收分批开展；框架单元、集成和已有体系短测不能全部延后。测试替身只证明接口和错误处理，不证明真实设备或科学正确性。

## 3. 调研结论如何落到本项目

以下为设计借鉴，不是立即安装或整库移植的依赖清单。

| 参考 | 借鉴点 | 本轮落点与不照搬的部分 |
|---|---|---|
| [MoSDeF / GMSO](https://github.com/mosdef-hub/gmso) | 结构、连接、相互作用和引擎表达分层 | 完成轻量模型与构建产物契约；不自研完整 GMSO 等价物 |
| [OpenFF Interchange](https://docs.openforcefield.org/projects/interchange/en/stable/using/collections.html) | 拓扑位置与带单位物理参数分离，保留应用映射 | 明确参数来源、模型映射和单位；不把格式转换成功当物理等价 |
| [Polyply](https://github.com/marrink-lab/polyply_1.0)及[原始论文](https://arxiv.org/abs/2105.05890) | 参数化拓扑与复杂初始坐标的构建 | 定义可承接链构建结果的边界；本轮不安装、不实现聚合物 |
| [RadonPy](https://github.com/RadonPy/RadonPy) | 将聚合物建模、平衡检查和性质计算组织为流程 | 引入质量规则与分析契约；具体平衡方法、性质算法以后按体系接入 |
| [atomate2 的 OpenMM 流程](https://materialsproject.github.io/atomate2/tutorials/openmm_tutorial.html) | 计算步骤组合、结构化任务输出及元数据/轨迹分离 | 轻量线性工作流和可组合分析，不引入数据库、任意 DAG 或整套调度器 |
| [MDCrow](https://github.com/ur-whitelab/MDCrow) | 将 MD 操作封装为 agent 工具 | 稳定工具契约、错误和任务级安全测试；不绑定特定 LLM 框架 |
| [GROMACS 长任务管理](https://manual.gromacs.org/documentation/current/user-guide/managing-simulations.html) | 原生检查点、输出一致性及继续计算 | 继续复用原生恢复机制，不编写自定义检查点转换器 |

这些项目覆盖不同层次；没有一个项目能够替代所有材料参数与科学验收。具体依赖、版本、许可证和平台组合，在真正接入时再核查和授权。

## 4. 目标职责与依赖方向

保持现有 specs、builders、scenarios、engines、runtime、workflows、analysis、research 目录。不增加并行 domain/core/platform 三套概念。

```text
CLI / agent 工具入口
           ↓
研究定义 → 冻结有限任务清单
           ↓
共用工作流：校验 → 构建 → 编译 → 执行/恢复 → 分析
           ↓
场景/构建器     GROMACS 适配器     分析器
           ↓
规格契约、能力规则、运行资源、证据存储
```

依赖约束：

1. 通用规格模块不导入具体引擎、场景实现、CLI 或研究编排。
2. 引擎模块解释原生文件与物理实现约束；不读取课题目录判断行为。
3. 场景决定装配步骤；不拥有另一套 runner 或隐式分析。
4. 研究层调用共用工作流；不直接操作 GROMACS 参数或检查点。
5. 分析输入是明确产物与映射，不依赖某个课题目录名。
6. 能力登记只引用已实现组件，规格类型本身不反向依赖登记器。
7. 使用普通函数、可序列化记录和显式映射即可；本轮不做动态插件发现、配置执行代码或多层继承。

## 5. 第一批：规格、模型与可替换组件

### 5.1 数据契约

下列字段名称和新模块均为拟议设计，不是现有可执行 API。P1 实施时冻结契约和最小示例，再进入运行格式变更。

| 契约 | 必须表达 | 首版实际支持 |
|---|---|---|
| ComponentSpec | 稳定组分 ID、模型引用、数量、用途角色 | 已有预参数化小分子；水的请求策略和实际生成数量显式记录 |
| ModelSpec | 身份/来源、分辨率、资产格式/哈希、结构与参数关联、适用限制 | 已有原生 GROMACS 资产，不猜 SMILES、质子化或参数 |
| InteractionBundle | 精确模型覆盖、全局约定、所需交叉项来源、用途与证据 | 保留现有完整性检查和 engineering_only 限制 |
| ScenarioSpec | 边界、盒子、区域、构建器标识及严格配置 | 已有正交周期盒、已有装填/填水/预建路径 |
| ProtocolSpec | 有序阶段、物理目标、状态交接、输出要求、后端参数引用 | 已有最小化与动力学线性流程 |
| ExecutionProfile | 工具/设备、有限预算、检查点策略 | 本地 CPU；GPU 参数和检查路径 |
| AnalysisRequest | 方法、输入角色、选择、窗口、单位与方法参数 | 现有水化接触和组分接触 |

具体处理：

- 通用层不把 .gro/.itp/.mdp 扩展名当成所有引擎的概念；通过带格式标识的资产和 engine_parameters 显式交给后端。
- 原生 MDP 模板继续是首版有效输入来源；提取可识别物理字段供校验、比较和记录，不重写完整 MDP 配置语言。
- 同一物理字段如果同时出现在阶段声明和后端模板，必须核对一致；冲突直接失败，不设隐式覆盖优先级。
- 保留单位明确的字段和转换表；不要求新增通用单位依赖，不接受“单位不明但可猜测”的值。
- 组分类型与体系角色分开；标记 solvent 不会自动赋予参数或生成浓度配方。
- 盒子表达可使用带单位的三条基向量和周期轴，但现有构建器仍拒绝未支持的非正交/非周期组合。
- 不在首版增加未消费的链长、交联反应、表面接枝等自由字段；将来由对应构建器的严格配置表达，通用层不假装已校验化学语义。
- 编译后必须报告全部实际组分、粒子/分子实例映射、总电荷及最终盒子；填水数与用户显式指定数量分开。
- 参数完整性、参数兼容性和科学适用证据分开。内容哈希不能代替力场兼容或模型验证。

### 5.2 构建与引擎接口

拟议责任，不要求每项都做成类：

| 组件 | 输入 → 输出 | 交接时必须检查 |
|---|---|---|
| 场景规划 | 已解析体系 → 有序构建步骤及适用性报告 | 每步有实现、输入齐全、不隐式改协议 |
| 构建器 | 冻结模型/几何/种子 → BuildResult | 请求/实际组成、映射、坐标和连接来源、盒子、参数资产 |
| 引擎编译 | BuildResult＋阶段协议 → PreparedStage | 原子顺序、有效参数、输入闭包、所需前序状态 |
| 阶段执行 | PreparedStage＋执行配置 → StageEvidence | 实际目标完成、数值日志、产物和检查点 |
| 分析器 | ArtifactSet＋分析请求 → AnalysisResult | 输入角色、时间、选择、单位及实现身份 |

BuildResult/PreparedStage 允许携带带格式说明的原生资产，不要求把全部势函数转换为自研中间表示。通用工作流不能解析其原生细节。

首批将已有预建和 Packmol 两条构建路径、GROMACS、两个现有分析器接入；它们是接口真实消费者。用测试内替身检查调度独立性，不发布假 LAMMPS、假聚合物插件。

### 5.3 能力判定与错误同源

为已实现组件建立轻量描述记录：标识、契约版本、接受的条件、依赖、输入输出角色、限制、证据引用。能力查询、配置校验与执行前检查调用同一组适用性规则，避免 CLI 手写另一份支持列表。

返回多维状态而不是一个 supported=true：

- implementation：implemented / not_implemented；
- compatibility：pass / fail / unknown；
- environment：available / unavailable / unknown / not_checked；
- engineering_evidence：通过记录的精确平台、模型和工具范围；
- scientific_evidence：not_assessed 或有范围的证据引用。

静态校验允许“GPU 配置合法但本机未检查”；执行前必须完成环境检查。任一未知状态不能自动当通过。

拟议错误结构包含 code、category、message、field、evidence_refs、recoverability；错误码至少区分 INVALID_SPEC、UNSUPPORTED_COMBINATION、MISSING_DEPENDENCY、BUDGET_EXHAUSTED、INTEGRITY_MISMATCH、RESUME_INCOMPATIBLE。是否可恢复由真实状态与检查点判断，不能由 agent 的文字选择决定。

## 6. 第二批：通用研究、分析和 CPU/GPU 执行

### 6.1 研究定义升级

首版仍使用有限的显式 cases，不做任意 JSON 路径覆盖、无限笛卡尔积、自动优化或动态执行代码。

- 每个 case 引用完整实验；定义中声明基线、变化因素、受控因素、重复、观察量和预算。
- 变化因素描述“哪些语义差异允许出现”，不替用户悄悄改配置。首批消费已有数量、场景和协议的可识别差异；未知差异拒绝自动比较。
- 场景和协议各自报告可变的种子槽。预建体系没有装填种子时不要求虚构 packing_seed；速度继承阶段不得重新赋种子。
- 研究层不直接调用 validate_packing 或 GROMACS 的 validate_protocol；通过统一实验校验入口复检每个展开任务。
- 重复种子策略显式声明。首版保留防止意外重复的检查，不把不同种子自动标为统计独立样本。
- 允许无分析的执行验收研究，以及多个已支持的分析请求；无观察量时不生成性质比较。
- 研究层保存“预期任务 → Run → AnalysisRun → 比较产物”的引用；Run 仍是执行状态的唯一事实来源。
- 单任务资源只引用统一 ExecutionProfile。批次仅管理 max_tasks、串行度、累计时间/存储和停止策略，不再维护第二套线程或 GPU 解释器。
- 首版串行；失败保留、后续未启动项保留，默认停止，不自动换参数/种子重试。

### 6.2 分析与比较契约

将水化接触、组分接触都接入同一结果封装，保留各自已有数值定义。通用字段至少包括：

- 源 Run、阶段和产物身份；
- 方法 ID/版本、实现身份与依赖版本；
- 指标 ID、单位、形状、选择定义、归一化；
- 时间范围、帧数、平衡段处理说明；
- 数值结果/表格引用；
- 数据完整性、工程检查、科学质量的分开状态。

比较器先按分析方法提供的兼容规则分组，再检查声明变量和受控条件。水化接触与组分接触不因单位相似而混合；不同观察量分别汇总。

decision_rules 从单纯文字升级为“研究说明＋受限结构化规则”。本轮实现已有工程事实的规则，例如阶段完成、必需产物存在、分析有效及全部声明任务到齐。规则返回 pass/fail/not_assessed，并保存依据。

可支持已存在数值指标的带单位范围检查，但无规则或缺少科学证据不能显示科学通过。自相关、有效样本量、置信区间、自动平衡识别和未实现物性算法留待后续，不能用空值或规则通过伪装已完成。

首版保留不完整批次禁止整体聚合的保守默认，仍列出每条成功、失败和未运行结果；未来若允许部分聚合，需独立明确规则，不能静默剔除。

### 6.3 执行配置与用途

ExecutionProfile 单独冻结，拟议字段按[已有执行方案](2026-09-14__execution__cpu-gpu-runtime__implementation-plan.md)收敛为：

- 工具定位、device、线程、单 GPU 可见编号、分阶段卸载策略；
- 构建/执行/分析墙钟预算、退出宽限、累计预算和 attempt 上限；
- 检查点间隔、存储停止阈值和最小磁盘余量。

物理步长、温压、目标步数及轨迹输出频率属于协议，不放入资源配置。CPU 可运行正式小任务，GPU 也可以短测；用途与设备无绑定关系。

用途策略分为 engineering_smoke、model_validation、production：

- smoke 保留现有有限规模、短程及科学未评估语义。
- model_validation 需要明确验证目标、协议、模型范围和有限预算；不跳过参数硬检查。
- production 需要适用范围、目标环境和协议审查的可追溯证据；不是把字符串改成 production 就解锁。
- 现有 engineering_only 模型不自动升级。测试夹具中的批准记录必须明显标识为测试数据，不能进入正式 catalog 充当验证证据。
- 工程实现可以测试非短测参数和拒绝分支；没有获准的科学模型时，production 对真实输入明确拒绝是正确行为。

首版一个本地进程、单 GPU、已有 thread-MPI 路线；不增加多节点 MPI、多 GPU 调优、SSH 或 Slurm 实现。只定义执行器提交/查询/停止/恢复的职责并完成本地实现，不发布空远程后端。

### 6.4 GPU 与有界长任务基础

- 从 profile 生成参数数组，不接受任意 shell 片段，不修改用户全局环境。
- CPU 模式明确走 CPU；GPU 请求不能静默回退。最小化走 CPU 是事先声明的策略，不算运行失败后的降级。
- doctor 报告引擎构建能力和可见设备信息；无法判定则 unknown。解析成功与设备可运行分开。
- 冻结请求策略，并从实际日志记录卸载结果；缺少可靠解析证据时不能声称 GPU 已参与。
- 将原短步数上限与格式/物理约束分开；非短测仍需正目标、有限预算和输出容量检查。
- 构建、编译、分析、退出宽限和恢复 attempt 都纳入预算；不能反复 resume 绕过总额。
- 正常预算停止优先请求原生检查点；强杀、缺检查点或 I/O 故障不能标为安全中断。
- 当前几何算法和模型规模限制继续保留；不把全部组分数、盒形和原子数限制当 CPU 限制取消。

## 7. 第三批：版本、存储和 agent 保障

### 7.1 格式迁移只做一次

拟采用 Experiment v3、Run v3、Research v2；三者版本独立，不因研究描述变化改动旧 Run。版本号在 P1 冻结，禁止各批次分别创建不同语义的 v3。

| 输入/产物 | 首版兼容策略 |
|---|---|
| 原 v1 实验/Run | 保留既有只读范围，不加入第二套旧 runner |
| 原 v2 实验 | 保留校验；新建任务时经受测试的确定性适配进入统一执行核心，记录原文哈希和转换报告，不覆盖源文件 |
| 原 v2 Run | 保留只读校验与有条件外部重分析；不自动补字段、不用新代码强行续跑 |
| 原 Research v1 源码 | 保留有限适配，生成新的冻结计划；记录来源和语义差异 |
| 已冻结旧计划/批次 | 只读审计，不重写账本或假装能由新版本无缝继续 |
| 新实验、Run 和研究 | 使用新契约与唯一核心；完整记录执行配置和身份 |

迁移入口需在实现时提供明确可审查方式。若输出配置文件必须显式指定新路径；只读 validate 不创建转换文件。构建新 Run 可在其独立 inputs 内记录转换产物，但必须报告 source_schema 与 resolved_schema。

旧模型来源缺失的信息标为未提供或阻止相关用途，不在迁移时猜测化学身份、许可范围或科学批准。纯表示迁移核查有效物理输入和必要数值，不以新 JSON 哈希不同误判模型改变，也不以文件名相同认定相等。

### 7.2 身份拆分与恢复

至少分别保存：

1. 模型和有效物理输入身份；
2. 构建实现、工具与实际构建结果身份；
3. 阶段执行实现、原生引擎和资源策略身份；
4. 分析请求、分析实现与依赖身份；
5. 整体软件版本作为诊断来源，不作为所有操作唯一兼容键。

不能简单删掉源码哈希。执行身份必须覆盖编译、进程、状态、存储等会影响恢复的传递依赖及运行资源；采用明确依赖清单、契约版本和测试，边界不确定时保守拒绝。

必测：仅改变分析器不阻止物理输入和执行实现完全相同的新格式 Run 恢复；改变实际执行依赖仍拒绝。旧 Run 不因该规则被追溯性放宽。

生命周期原则：

- 未完成且具有有效检查点的 interrupted 可在同一 Run 增加 attempt，预算累计。
- completed 或已封存的失败/取消/不确定 Run 不原地重开。
- 改目标、协议、模型、引擎构建或服务器，建立新 Run，必要时引用父证据。
- 不提供 force 跳过校验，不做 Mac 到 Linux 检查点迁移保证。
- 不要求 CPU/GPU 或不同平台产生逐字节相同的动力学轨迹。

### 7.3 产物与持久化存储

首版使用明确的本地持久化目录，不引入数据库或云存储；路径由用户配置，不写死外置盘和个人服务器路径。

将产物按角色管理：冻结输入、有效编译输入、可变运行输出、检查点、封存 attempt、分析和比较结果。身份使用逻辑角色＋相对路径＋哈希，绝对路径只用于定位。

- 活动输出允许引擎原生 append；封存证据必须不可被后续 append 改写。
- 继续保留安全副本路线，不用可变文件硬链接冒充不可变快照。
- 构建、恢复和分析复制前，估算帧数、已有副本及磁盘开销；估算注明不确定性。
- 用有界巡检和登记产物信息降低高频全目录扫描成本；关键封存、分析和恢复前仍做完整性检查。
- 磁盘阈值是停止机制，不是操作系统硬配额；为检查点和退出保留余量。
- 源轨迹不足、复制失败或超预算明确拒绝，不自动清除历史结果。
- 增加清单完整性复查和隔离副本恢复测试；不在本轮自动移动 /private/tmp 中的旧验收证据。
- 现有副本策略无法承受的超大轨迹明确不支持。分段轨迹、对象存储和去重缓存以后单独设计。

### 7.4 Agent 工具契约与安全测试

优先完善现有 CLI，不安装 LLM 框架，不新增需要 API 密钥的 agent 服务。

- 只读与写入操作明确标注；plan 默认预览，build 不伪装成只读。
- JSON 输出包含契约版本；参数解析失败也采用可识别的机器错误，不只处理运行时异常。
- 写入要求明确输出根；工具不能从研究配置执行任意脚本或把参数拼成 shell。
- 错误中保留可追溯位置和所需下一步，避免泄露整份环境或凭据。
- 预算和模型用途保护落实在程序；AGENTS/skills 只负责指导，不代替校验。
- 建立不依赖付费模型的任务级契约测试：正确预检、不支持拒绝、预算超限、无 GPU、身份不匹配、重复提交、中断恢复、失败保留、工程结果不得冒充科学通过。
- 这些测试验收的是工具，不是 LLM 自主科研成功率。真实 agent 评测和操作系统权限隔离另行安排；有 shell 权限的外部 agent 不受 CLI 文档构成的安全沙箱保护。

## 10. 验收矩阵与预算

### 10.1 不需要新材料或 GPU 的必测项目

| 验收层 | 必须证明 |
|---|---|
| 依赖方向 | 通用规格不导入 GROMACS；研究不直接操纵 MDP/装填；底层不导入 CLI |
| 配置与迁移 | v2 来源不变、转换可追溯；非法字段、冲突物理参数和未知组合拒绝 |
| 能力/错误 | 查询与实际校验同源；静态合法、环境未知与科学未评估分开 |
| 研究扩展 | packed 与预建实验都能组织；有/无装填种子的重复正确；两个现有分析器不需改研究调度 |
| 比较 | 未声明差异、不同单位/方法/窗口不可误聚合；失败与未启动不丢失 |
| GPU 逻辑 | 参数数组、分阶段策略、缺能力/设备未知/无实际卸载证据等拒绝路径 |
| 预算 | 构建、执行、分析、宽限、恢复均计费；重复调用不能增加预算或重复提交 |
| 身份/恢复 | 只读与执行分开；源码依赖、协议、工具改变不可绕过；有效中断恢复 |
| 存储 | 复制前拒绝超容量、源变化拒绝、封存输出不随 append 改变、完整清单复查 |
| 安装与工具 | 仓库外可用，发行包不漏模块，机器错误稳定，预览不启动引擎 |

增加测试内的构建/分析替身，验证工作流消费接口而非硬编码具体类；这些替身不能加入公开能力表。真实路径仍以现有构建器、引擎和分析器做交叉验证。

### 10.2 真实 macOS CPU 回归

实施和小量计算获得授权后，复用已有环境，保持原模型、力场、电荷、水模型及原协议模板不变；必要派生配置另存并记录差异。

至少覆盖：

- 现有四个装填场景：ZIL 水盒、CAT/ANI 水盒、三组分水盒、ZIL 无水周期盒。
- 已有预建路径的真实最小正例，证明研究不只会展开 packed。
- 两个条件、每条件两个重复的研究闭环；全链路保留所有声明任务。
- 受控中断后同一目标恢复，实际核查检查点、步数和输出。
- 两种已有分析封装的数值回归，其中接触计数继续独立算法对照。
- 只读旧 Run 与隔离副本篡改负例；不得篡改正式证据做测试。

建议每批真实验收 CPU 2 线程、串行、动态阶段沿用现有每段不超过 2,000 步的短测配置；单次执行 180 秒、最多 2 次 attempt。整批含构建/分析/宽限建议上限 30 分钟、输出停止阈值 1 GiB。具体任务数在启动前列明；预算不足停止，不自动加时或提高容量。

非短测策略的核心分支可用小目标和测试数据验证，不能伪造真实模型的 production 批准。长时间稳定性、正式科学协议和大轨迹吞吐另行验收。

现有测试命令如下，仅供后续实施使用，不是本次运行记录；从仓库根、使用已核实存在且依赖满足的解释器：

```sh
PYTHONPATH=src zwitterion_hydration_md/.venv-macos-analysis/bin/python -B -m unittest discover -s tests -v
```

如解释器缺失或依赖不符，报告并确认环境调整，不自动安装。新增 CLI 参数和验收命令必须在实现后从解析器生成文档，本文不列不存在的可执行命令。

### 10.3 无对应环境时怎样交付

- macOS CPU：记录真实执行的版本、测试数、Run 和限制。
- Linux：准备独立环境说明和同一验收入口；没有 Linux 运行证据则待验收。
- GPU：参数和日志夹具测试通过不等于 GPU 验收；真实 GPU 需核对实际卸载、固定初态的适当数值对照和恢复。
- CI：可在实施获准范围内提供自动化配置；若涉及依赖安装、凭据、runner 或额外 CI 权限，先确认。不能把 CI 文件存在当远端运行通过。
- 科学：全部未评估项保持 not_assessed；不为展示框架完整而生成科学通过记录。

## 11. 本轮不做与以后怎么接入

本轮不安装 Polyply、mBuild、GMSO、OpenFF、RadonPy 或新引擎；不实现交联聚合、任意混合溶剂、晶体/纳米表面、反应力场；不接远程调度、数据库、Web UI 或 LLM 服务；不清理旧案例、环境、原始数据和历史输出。

后续一类能力的交付单元是“能力包”这个逻辑集合，不要求现在创建新的包管理系统：

1. 模型/方法来源与适用约束；
2. 需要的构建器、场景或分析实现；
3. 共享资产与一个最小示例；
4. 单元/拒绝负例及真实工程证据；
5. 具体科学验收方案及已取得的证据。

接口内的聚合物构建可由 Polyply 等适配器实现；但未知单体、交联、表面接枝等必须有其自身模型与验证。不同场景只组合经过支持判定的步骤，不能用“能够填进一个盒子”代替混合体系适用性。
